## 2. I — 洞察（四元组）

### I1　"声明一致"不等于"组合一致"

- **现象**：CI 能保证每个子项目的 pyproject 与实现一致，也能保证 `libs/` 不反向依赖，但无法回答"把 A、B、C 三个库装进同一个进程后是否仍然自洽"。
- **根因**：一致性断言作用于**单包静态事实**，而组合正确性是**跨包运行期性质**；当前没有"服务身份"这一层，跨包关系只能退化为 import 图（编译期、全序、不可替换）。
- **影响**：任何能力替换（例如把 `caffe-ffi` 换成 `npu-ffi` 后端）都必须改代码并重建，而不是改配置；`xs` 无法给出"装配是否可解"的答案。
- **建议**：引入能力键作为跨包唯一身份（D2），把 import 图升级为**声明依赖图**，并在 CI 中做可解性判定（D5）。

### I2　缺少"撤销"语义，使可选能力退化为编译期开关

- **现象**：`xuan-compose` 用静态处理器表分派命令；`xs` 用 14 行 import 装配命令；`okf` 卸载时吞掉异常。三者共同点是"登记即副作用，撤销无证据"。
- **根因**：登记动作（向全局表写入、注册回调、挂载钩子）没有统一返回句柄，导致"谁登记、谁负责撤销、撤销是否彻底"不可判定。
- **影响**：插件只能"加载后重启"，无法在同一进程内做 A/B 能力切换；测试无法验证残留；Koishi 式"禁用即撤销"（F12）在 xuanspace 无法成立。
- **建议**：把 `Disposable` 上升为契约（D3），并以 AST/运行时双通道检出裸副作用；卸载残留纳入门禁。

### I3　静态装配违反开闭原则，新增能力的边际成本落在核心文件

- **现象**：新增一个 `xs` 子命令需要改 `cli.py`（S5）；新增一个 compose 指令需要改处理器表（S8）；`okf` 新增插件需要改自身 pyproject 的 `[tool.okf.plugins]`（S14）。
- **根因**：装配点被写死在"核心"中，扩展点只存在于目录约定层，没有 `entry_points` 之类的第三方贡献通道。
- **影响**：核心文件的改动频率与生态规模线性相关；合并冲突集中；`apps` 无法在不触碰 `tools` 的前提下扩展 CLI。
- **建议**：装配输入改为"静态声明 + entry points 双通道"，核心代码只保留解析器（对论文 §5.2 加载器的直接移植）。

### I4　"快照 vs 磁盘"是双真相，本质是缺少唯一权威视图

- **现象**：声明快照记录 `cli_commands/lib_projects/submodules`，CI 比对快照与实现；子模块指针漂移需要另立 G 类断言补救（S4、S16）。
- **根因**：快照是"人对系统的描述"，磁盘是"系统本身"，二者之间没有**由系统计算得出**的推导关系，只能靠人工同步 + 事后断言。
- **影响**：每次结构变更都要人工改快照，门禁报错时难以区分"真漂移"与"快照过期"；这正是论文用 committed view 取代"人工清单"的动机（F8–F11）。
- **建议**：快照降级为**产物**而非输入：由 `xuan.plugins.lock` + 磁盘解析自动生成，CI 只断言"可重现"（同输入 → 同输出），不再人工维护（D4）。

### I5　`okf` 已是论文的最小实现，但"位置"与"身份"两处使其实用性受限

- **现象**：`okf` 完整具备 Context/Fiber/Disposable/拓扑装配/epoch 重载，却只服务 `tools` 内部；epoch 用 `id(impl)`（S12），跨进程/跨机器不可复现。
- **根因**：① 归属 `tools/` 触发依赖方向红线（S3/S15）；② 用对象地址作身份，把"实现等价"退化为"内存同一"，与论文"提交视图是配置的函数"（F11）相悖。
- **影响**：kernel 无法被 `libs/` 复用，每个库只能各自造轮子；同一 lock 文件在不同进程得到不同 epoch，装配结果不可比较，无法做 CI 对账。
- **建议**：下沉为 `libs/xuan-plugin`（D1），epoch 改为 `(plugin_id, impl_version, config_digest)` 的结构化摘要；持久化与跨进程可比。
