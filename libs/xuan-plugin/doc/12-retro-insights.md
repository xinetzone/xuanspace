## 二、I 阶段：洞察（G2）

### 洞察 1：缺陷在「修复的缝隙」中呈链式出现，而非各自独立

- **现象**：六轮改动依次为七态化 → 热替换事务 → 通知批处理 → 身份摘要 → error 与迁移表机检 → 可解性互锁；每轮触发点都落在上一轮新引入的边界上（F1–F6）。
- **根因**：状态机是「多维不变量联合体」——状态合法性、效应零残留、身份稳定、通知收敛、输入可解五条约束彼此耦合；按可见路径逐条验证时，覆盖的是现状组合而非约束空间。
- **影响**：不写机检的修复只能保住当前路径，后续修复会重新打开旧缺口；改动量与回归风险随提交序线性累积（F7：+1802 行）。
- **建议**：每轮把本轮确立的不变量升级为穷举或条件机检（P2-8 的 7×7 穷举、P2-9 的 `ACTIVE ⇒ 输入可解`），使不变量集合单调增长、可被下一次改动自动守护。

### 洞察 2：单点修复会生成「第二真相」，删除下游兜底比新增兜底更重要

- **现象**：P2-8 在 `assembly.py` 发现按 `id(exc)` 去重，与 `Fiber.error` 并存；本轮删除该去重后，失败清单仍无重复（F26）。
- **根因**：补丁层倾向于在就近位置兜底，以最小改动掩盖上游语义未收口；兜底一旦落地，就成为与主语义并行的第二套判据。
- **影响**：地址式判据不可跨进程复现，且两套判据对「同一失败是否已处理」可给出不同答案。
- **建议**：修复顺序固定为「先修上游语义 → 再删下游兜底 → 最后用测试证明删除安全」；凡保留兜底，必须在台账 Notes 中写明其存在理由与退出条件。

### 洞察 3：可观测性决定可测试性，收敛责任应下沉到发生点

- **现象**：P2-9 的破缺在最终视图上会自愈——事务排空后依赖方被再刷新一次即回到 INACTIVE；只有在事务未排空时断言才能观察到「ACTIVE + 输入不可解」。触发撤销的 `notify` 还可能在 `LOADING` 期被 `_refresh` 早退吞掉。
- **根因**：正确性被隐式托付给传播链（「稍后会有通知来修」），而传播链的正确性又依赖被修复对象自身所处的状态。
- **影响**：缺陷在常规回归中不可见，却在嵌套事务与真实装配器路径上构成非法中间态（外部读到 `ACTIVE` 后 `ctx.get` 抛 `KeyError`）。
- **建议**：收敛责任下沉到发生点（`_reload` 自行判定终态），传播只承担「加速与去抖」，不承担正确性；测试显式构造「事务未排空」窗口。

### 洞察 4：门禁数字是复盘的客观锚点，须按「基线 + 增量」记录

- **现象**：每轮台账都记录两批测试数、lint/format/mypy 规模、脚本扫描计数与实机对账结果（F10–F19）；`libs/mystx` 漂移因此可被明确归因为「既有、与本轮无关」。
- **根因**：测试总数与扫描计数是少数不依赖叙述的客观量；缺失基线时，「未新增失败」只能靠声明。
- **影响**：没有基线就无法区分「本轮引入」与「历史遗留」，评审只能全量重跑。
- **建议**：固定四元组记录法——「上一轮基线 / 本轮实测 / 差值 / 既有失败清单」，并在提交信息中给出，使任何一轮都可被独立复核。

### G2 结论

四元组洞察 4 条（现象 / 根因 / 影响 / 建议齐备），**G2 通过。**
